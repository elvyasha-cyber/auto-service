# Auto Service

Сайт заявки автосервиса и закрытый API. Клиент заполняет форму в браузере. Мастер входит в свою панель: там каталог услуг, очередь заявок и статистика поведения на странице. Всё это хранится в Postgres.

Снаружи сайт открывается только через порт 443. Backend, Postgres и Watchtower снаружи не публикуются. pgAdmin и Registry выключены.

Рабочая папка на сервере: `/root/auto-service`.

## Что нужно

- Docker и Docker Compose.
- Файл `.env` в корне проекта. Пароли задаются на сервере. В архив для проверки он входит. В публичный репозиторий его не кладут.
- Node.js и npm нужны только чтобы заново собрать страницу. Уже собранный сайт лежит в `dist`, Nginx отдаёт его без Node.

## Файл .env

```
POSTGRES_USER=
POSTGRES_PASSWORD=
POSTGRES_DB=
PGADMIN_DEFAULT_EMAIL=
PGADMIN_DEFAULT_PASSWORD=
REGISTRY_USER=
REGISTRY_PASSWORD=
SECRET_KEY=
```

`REGISTRY_PASSWORD` совпадает с `POSTGRES_PASSWORD`. Почта pgAdmin: `admin@auto-service.ru`.

`SECRET_KEY` нужен для входа мастера. Его генерируют командой `openssl rand -hex 32`. Без этого ключа панель не пускает внутрь.

Пустой образец этих строк, без паролей, лежит в `.env.example`.

## Установка

В папке проекта:

```bash
bash create-user.sh
docker compose up -d --build
```

`create-user.sh` читает `.env` и записывает пользователя Registry в `auth/htpasswd`. Сам сайт этот файл сейчас не использует: Registry выключен. Скрипт нужен, чтобы поднять проект заново.

Проверка контейнеров:

```bash
docker ps --filter name=auto-
```

Должны быть запущены `auto-nginx`, `auto-postgres`, `auto-backend`, `auto-watchtower`. `auto-pgadmin` и `auto-registry` при этом запуске не поднимаются.

Если менялись файлы в `backend`, контейнер пересобирают так:

```bash
docker compose up -d --build backend
```

## Сборка страницы

Команды выполняются в папке `frontend`, на компьютере, где установлен Node:

```bash
npm install
npm run build
```

Vite кладёт готовую страницу в `dist` на уровень выше. Эту папку нужно скопировать на сервер в `/root/auto-service/dist`. Nginx подхватывает файлы сразу, контейнер перезапускать не нужно. После копирования страницу обновляют через Ctrl+F5.

Собирать страницу нужно из заготовок на компьютере. В них есть очередь заявок. Готовые файлы в `dist` сервер только отдаёт, сам их не собирает.

## Как открыть

Адрес сервера подставляется вместо `IP`. Протокол `https`.

| Что | Адрес |
| --- | --- |
| Страница клиента | `https://IP/` |
| Панель мастера | `https://IP/admin` |
| Описание API `/docs`, `/redoc`, `/openapi.json` | закрыто, ответ 403 |
| pgAdmin и Registry | выключены |
| Порт базы 5432 снаружи | ответ 403, это не сама база |

Это две разные страницы. На главной ссылка «Вход для мастера». В панели ссылка «К заявке клиента».

На этом сервере порты 80 и 443 уже заняты общей дверью. Сайт висит на ней по адресу `https://IP/`. Старый адрес с портом `:8088` больше не открывается. Сертификат у общей двери безымянный: браузер предупредит. Нужно нажать «Дополнительно» и перейти на сайт.

Прямой заход на порт backend снаружи невозможен: у контейнера нет опубликованного порта. Порт `8000` на этом сервере принадлежит другой панели, его не занимают.

## Две страницы

Страница клиента читает каталог услуг запросом `GET /admin-data`. Клиент выбирает услугу из списка или пишет свою, указывает бюджет «от» и «до» и может добавить несколько способов связи. Кнопка отправки сохраняет заявку. Текст успеха: «Заявка у мастера».

Панель мастера сначала показывает вход. Логин и пароль проверяются по таблице `admins`, в базе лежит только хеш пароля. Кнопка «Зарегистрироваться» видна, только пока в `admins` никого нет. После входа на странице три блока: очередь заявок, каталог услуг и статистика пользователей.

Очередь читается запросом `GET /leads/queue`. Температура считается в этот момент, отдельной колонки «срочно» в базе нет. Горячие заявки сверху. Кнопка «Просмотр» открывает одну заявку: срок, бюджет, отдел, нужен ли менеджер и как связаться.

Каталог услуг — таблица `admin_data`. В панели её можно пополнить, изменить и удалить. Форма клиента в эту таблицу не пишет, она только показывает готовый список.

## Две разные метрики

Их легко смешать. Это разные таблицы и разные моменты записи.

`lead_metrics` пишется один раз, вместе с заявкой. Кнопка отправки делает два запроса:

1. `POST /leads` — данные формы, строка в `leads`.
2. `POST /lead-metrics` — одна строка на эту заявку.

В `lead_metrics` лежат время на странице к моменту отправки, нажатые кнопки, паузы курсора и число повторных визитов. Строка связана с заявкой полем `lead_id`. Если заявку удалить, эта строка удаляется вместе с ней. Если заявка записалась, а метрики нет, клиенту всё равно показывается успех.

`behavior_metrics` к заявке не привязана. Пока открыта главная страница, браузер раз в секунду отправляет `POST /behavior-metrics`. Каждая секунда — новая строка: время на странице, кнопки и положение курсора. Если человек ушёл на другую вкладку, запись встаёт на паузу. В панели кнопка «Статистика пользователей» читает эти строки и показывает среднее время за сутки, 7 дней и 30 дней и карту курсора. Точка `0,0`, пока мышь ещё не двигали, на карту не попадает.

## Пять таблиц

Их создаёт backend при старте. Отдельный файл миграций не нужен.

- `leads` — заявка: имя, бизнес, бюджет одной строкой «от … до …», способы связи, комментарий, ниша, размеры, срок, тип задачи, услуга, удобное время, телефон, почта, Telegram, WhatsApp и Макс.
- `lead_metrics` — одна строка на заявку, связь по `lead_id`. Это итог в момент отправки, не посекундный дневник.
- `admin_data` — каталог услуг: название и диапазон бюджета.
- `admins` — мастера: логин и хеш пароля.
- `behavior_metrics` — посекундный дневник главной страницы. Номера заявки в ней нет.

## Где смотреть логи

```bash
docker logs auto-backend
docker logs auto-nginx
```

Следить за новыми строками: добавить `-f` и выйти через Ctrl+C.

## Что не выкладывать

Файл `.env` и `auth/htpasswd` содержат пароли. В публичный репозиторий эти два файла не кладут.
